## 0. 先读这一段：为什么要重构

这是知乎黑客松 2026 参赛作品「观点进化缸」。产品把一个知乎问题下的回答渲染成生态系统：
每条回答 = 一个物种，**立场**（6 类）= 物种类别，**生存策略**（6 类）= 它靠什么活下来。

**今天（2026-09-13）实测发现一个致命的架构错配：**

现有代码把知乎**直答 API**（`zhida-fast-1p5`）当成一个「输出 JSON 的分类器」在用：
给它 system prompt「严格只输出 JSON 数组」+ 10 条回答摘要，期望拿到 `[{n,stance,strategy,summary}]`。

**实测结果：直答完全无视 system prompt 和格式要求。**
它是一个**问答 / 检索产品**，不是通用指令执行器。它从输入里认出了那个知乎问题，
然后返回了一篇 1500 字的知乎风格长回答（带「澎湃新闻、大河报等多源报道一致」这类检索来源），
完全没有 JSON。

原始响应证据在 `docs/evidence/zhida-raw-2026-09-13.json`（我已落盘，请先读它）。

**后果**：`annotateSpecies()` 的 `extractJson` 必然抛异常 → 走 catch 分支 →
**每条回答都被标成 `stance:'中立', strategy:'数据论证', annotationSource:'none'`**。
本地四个已构建的生态缸、40 个物种，**全部是同一个灰色的「中立·数据论证」**。
可视化就是一坨同色圆点，产品的核心概念完全没有被呈现出来。

**这不是额度问题**（额度确实也很紧，见下），**是设计问题**。

### 额度现实（比官方文档严苛得多，今日实测）

| 能力 | 文档宣称 | **实测日额度** |
|---|---|---|
| 直答 `zhida_openai` | 100/日 | **2/日** |
| 热榜 `hot_list` | 100/日 | **2/日** |
| 知乎搜索 `zhihu_search` | 5000/日 | **10/日** |

| 知识库 `knowledge` | — | 500/日 |

**直答 2 次/日**意味着：评委在 Demo 现场点两下，AI 能力就没了。
**任何把主流程建立在直答之上的设计，都会在评审当天失败。**

## 1. 目标架构（这是已定的决策，不是备选建议）

把「逐条标注」和「AI 解说」拆成两件独立的事：

```
                 ┌────────────────────────────────────────┐
                 │ A. 逐条标注（每个物种的立场 / 策略）        │
生态缸构建 ──┤    │    → 本地启发式标注器                    │
             │    │    → 零额度、确定性、可解释、永远可用      │
             │    └────────────────────────────────────────┘
             │    ┌────────────────────────────────────────┐
             └────│ B. 生态解说（整缸一段叙事）                │
                  │    → 直答，自然语言提问，不强求 JSON       │
                  │    → 额度耗尽时降级为本地模板叙事，不阻断    │
                  └────────────────────────────────────────┘
```

**为什么这样分工是对的：**

- 逐条 6 分类是**结构化判别任务**，恰好是直答最不擅长的（它是问答产品）；
  而中文立场 / 修辞的表层特征非常显著，**词典 + 规则可以做到可用**，
  且**可解释性反而变成产品卖点**——评委能展开看到「为什么判成反讽」，
  这比一个黑箱 LLM 标注更有说服力。
- 生态叙事是**开放式问答**，恰好是直答最擅长的。实测它在这个方向输出质量很高
  （证据文件里那篇长回答其实已经自发地做了观点分派：「支持方认为…质疑方认为…还有一种更现实的解读…」）。
- 主流程零直答依赖 → 评委随便点都不会挂。

## 2. 任务 A：本地启发式标注器（核心交付物）

新建 `app/server/src/annotator.js`。

### 2.1 输入 / 输出契约

```js
/**
 * @param {string} question 知乎问题标题
 * @param {object} item     { excerpt, votes, comments, authority, editTime, author, badgeText }
 * @param {object} ctx      { questionType }  由 classifyQuestion() 预先算好，整缸共用
 * @returns {{
 *   stance: '支持'|'反对'|'中立'|'解构'|'反讽'|'补充',
 *   strategy: '数据论证'|'情绪共鸣'|'故事叙事'|'身份站队'|'抖机灵'|'引用权威',
 *   confidence: number,   // 0..1，两个维度取较低者
 *   evidence: {
 *     stance:   Array<{ term: string, weight: number }>,  // 命中证据，按贡献降序，最多 5 条
 *     strategy: Array<{ term: string, weight: number }>,
 *   },
 * }}
 */
export function annotateOne(question, item, ctx)

export function classifyQuestion(title)       // → { type: 'judgement'|'why'|'howto'|'open', matched: string[] }
export function annotateAll(question, items)  // → { items: [...带标注], annotationWarning: string|null }
```

### 2.2 阶段一：问题类型判别（决定 stance 的先验）

中文知乎问题大致四类，**它们的立场空间完全不同**，这是准确率的关键前置：

| 类型 | 触发句式 | stance 先验 |
|---|---|---|
| `judgement` 判断型 | `如何看待` `怎么看` `是不是` `该不该` `值不值` `算不算` `对不对` `…吗？` | 支持 / 反对活跃 |
| `why` 归因型 | `为什么` `为何` `原因` `是何原因` | 偏 中立 / 补充 / 解构 |
| `howto` 求解型 | `如何…` `怎么办` `怎样` `有哪些` `推荐` | 偏 中立 / 补充 |
| `open` 开放型 | 其余 | 均匀 |

对 `why` / `howto`，**支持 / 反对的打分要乘一个衰减系数（建议 0.55）**，
否则会把「解释性回答里顺带出现的肯定词」大面积误判成「支持」。

### 2.3 立场（stance）打分

每个 stance 维护一个特征集，特征 = `{ pattern: RegExp|string, weight: number, note: string }`。
`score[stance] = Σ 命中权重`，取 argmax。

**最低要求覆盖以下特征（可以扩充，不可缺失）：**

- **反对**：`不敢苟同` `并非` `未必` `恰恰相反` `我不信` `不靠谱` `站不住脚` `纯属` `所谓的`
  `翻译一下就是` `说得好听`；否定副词密度（`不` `没` `别` `无` 每百字出现率 > 3 加分）
- **支持**：`确实` `的确` `没错` `说得对` `同意` `我赞成` `值得肯定` `已经属于` `属实是好事`
- **解构**：`这个问题本身` `伪命题` `问错了` `真正的问题是` `换个角度` `先别急着`
  `我们先定义` `本质原因是什么` `本质上是` `拆解一下`
- **反讽**：`懂的都懂` `多谢款待` `狗头` `学会了` `支个招` `熟悉的配方`；
  引号包裹褒义词（`"格局大"` `"情怀"`）；`？！` 连用；反语句式（褒义词 + 后文否定）
- **补充**：`补充一点` `另外` `顺便` `还有一个角度` `以上答案` `没人提到` `我再说一个` `对比一下`
- **中立**：**不设正向特征**；所有分数低于阈值时落到中立

**反讽与解构极易互相误伤**：给反讽更高的单特征权重，但要求 **≥2 个特征同时命中**才允许判反讽。

### 2.4 生存策略（strategy）打分

| 策略 | 判别特征 |
|---|---|
| **数据论证** | 数字密度（阿拉伯数字 / `%` / `万` `亿` `倍` `元` / `月薪\d+`）、编号列点（`1.` `第一，`）、`数据显示` `统计` `占比` `平均` `根据…报告` |
| **引用权威** | 书名号 `《…》`、`第\d+条`、`法律规定` `劳动合同法` `专家` `教授` `论文` `官方` `白皮书`、脚注标记 `[1]` `[2]` |
| **故事叙事** | 第一人称 + 过去时间词（`那年` `当年` `后来` `记得` `有一次` `\d{4}年，我`）、具体人名/地名/金额同现、时间推进链（`先…然后…后来`） |
| **情绪共鸣** | 情感词（`累` `熬` `心疼` `委屈` `愤怒` `无奈` `扛不住` `真心觉得` `说出了心声`）、感叹号密度、`我们都` |
| **身份站队** | `作为一个` `我们\w{1,4}人` `打工人` `985` `文科生` `过来人` `在单位待久了` `同行`；群体对立（`老一辈` vs `年轻人`、`甲方` vs `乙方`） |
| **抖机灵** | 平均句长 < 18 字 + 转折收尾；谐音 / 双关；`建议` 开头的荒诞提案；梗式表达（`熟悉的配方，熟悉的味道`）；括号吐槽 |

**互斥修正（必须实现）：**

- 数据论证与引用权威高度共现 → 若两者都命中，`《》` / 法条 / 脚注 特征应压过纯数字（**引用权威优先**）
- 故事叙事与情绪共鸣共现 → 若第一人称过去时叙事特征强，判**故事叙事**

### 2.5 置信度与低置信降级

- `conf = clamp((topScore - secondScore) / (topScore + 1e-6), 0, 1)`，再乘一个命中数因子
  （命中 0 个特征时 conf = 0）
- `confidence = min(stanceConf, strategyConf)`
- `confidence < 0.15` 时：
  - stance 强制落 `中立`，strategy 保留 argmax
  - evidence 里放一条 `{ term: '特征不足', weight: 0 }`
  - 前端会据此显示「低置信」角标 —— **这是诚信要求，不许把低置信伪装成高置信**

### 2.6 分布健康检查（防退化，**非可选项**）

`annotateAll()` 在返回前做一次后处理：

- 若 **≥80% 的物种落在同一个 stance** → `annotationWarning: '立场特征稀疏，多数物种落入同一类，标注可信度低'`
- strategy 同理
- 服务端把这个字段透传给前端展示

**现状就是 100% 落在「中立·数据论证」而系统毫无察觉。这条检查就是为了让这种失败变成可见的。**

## 3. 任务 B：直答通道改造（从「分类器」改成「生态解说员」）

### 3.1 拆掉现有的 JSON 强制路径

### 3.2 新增「AI 生态解说」

新增 `explainEcosystem(question, species)`，**自然语言提问，不加格式约束的 system prompt**：

```
在知乎问题「{question}」下，目前主要存在哪几种不同立场的观点？
每一派分别靠什么方式说服读者——是摆数据、讲个人经历、调动情绪、
诉诸身份认同、引用权威，还是靠抖机灵？请分派说明，并指出哪一派目前最占上风。
```

- 模型用 `zhida-thinking-1p5`（深度档），**一缸只调一次**
- 返回值就是**纯文本 / markdown**，原样存进 `ecosystem.aiNarrative`
- **失败或额度耗尽 → `aiNarrative: null`，不抛异常，不阻断整缸构建**
- 记录 `aiNarrativeSource: 'zhida-thinking-1p5' | null` 与失败原因 `aiNarrativeError`

**硬要求：整缸构建绝不能因为直答不可用而失败。** 本地标注器已经把主流程撑起来了。

### 3.3 放生分析同样去 JSON 化

`analyzeRelease()` 现在也是「要求直答输出 JSON 对象」，同样注定失败。改为：

- **数值部分**（存活概率、压制来源、风险、杂交建议）→ 完全由 `ruleModel.js` 产出
  （已实现，公式透明，保留不动）
- **草稿自身的 stance / strategy** → 用**本地标注器** `annotateOne()` 标注草稿文本（零额度、即时）
- **可选的 AI 点评** → 自然语言问直答：
  ```
  如果在知乎问题「{question}」下发布这样一条回答：「{draft 前 800 字}」，
  它可能会遭到哪些已有观点的反驳？读者最可能在评论区提出什么质疑？
  ```
  返回纯文本存 `aiComment`，失败则 `null`
- `analysisSource` 取值改为 `'rule+local'`（无 AI）/ `'rule+local+ai'`（有 AI 点评）

### 3.4 额度守卫

- `ZHIDA_DAILY_LIMIT` 默认保持 2
- **新增**：一个缸的 `aiNarrative` 一旦拿到就随缸持久化（`eco-cache.json` 已有磁盘持久化，跟着走），
  重复访问永不再调直答

2. **它标注了来源**（「搜索结果1、5、9」），说明它对该问题下的回答做了真实检索，不是凭空生成。
3. **它给出了「谁占上风」的判断**，正好是生态叙事需要的收尾。

## A3. 因此追加一个交付项（任务 B+）

除了把整段文本存进 `ecosystem.aiNarrative`，请**再做一层轻量解析**，导出结构化的「派系」：

```ts
// Ecosystem 追加字段
aiFactions: Array<{
  name: string;        // 派系名，例：「法律拆解派」
  claim: string;       // 代表观点（「**代表观点**：」后面那段，截断到 120 字）
  persuasion: string;  // 说服方式（「**说服方式**：」后面那段，截断到 80 字）
}> | null;
aiDominant: string | null;   // 「哪派最占上风」小节的正文，截断到 200 字
```

解析要求：

- **纯正则 / 字符串解析，不要再调一次直答**
- 按 `^##\s*[一二三四五六七八九十]+、` 或 `^##\s*\d+[.、]` 切分派系小节；
  小节标题里的引号内容（`"…"` / `「…」`）可作为副标题，主名取引号前的部分
- 派系内按 `\*\*代表观点\*\*：` 与 `\*\*说服方式\*\*：` 取值，取不到就留空字符串
- `哪派最占上风` / `谁最占上风` / `占上风` 开头的小节 → `aiDominant`
- **解析失败必须优雅降级**：`aiFactions = null`，但 `aiNarrative` 原文照常保留展示。
  绝不能因为解析失败就丢掉那 1300 字的真实 AI 产出。
- 给这个解析函数写单测（用附录里那段真实响应做 fixture，
  从 `docs/evidence/zhida-explain-2026-09-13.json` 里读 `rawResponse` 提取 content）。
  再补一条「格式完全不符的输入 → 返回 null 且不抛异常」的用例。

这样产品就有了**两层生态**：
- **物种层**（单条回答，本地可解释标注器，零额度，永远可用）
- **派系层**（整缸归纳，知乎直答，额度允许时才有，随缸永久缓存）

两层由不同方法独立得到，互相印证——这正是产品说明里要讲的「双通道交叉验证」。
